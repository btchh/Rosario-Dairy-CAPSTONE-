## Backend fix: slow response to stalled Redis

Pausing QA Redis reproduced a safe JSON 503 taking **15.073 seconds** on an
invalid checkout. Multiple cache reads accumulated the client's socket timeouts
before the throttle decision, exceeding the frontend's 15-second request limit.

`config/settings.py` now uses one-second cache connection/operation timeouts
with no implicit retries. The same outage returned JSON 503 in **3.053 seconds**.
After Redis resumed, validation returned its normal 400. This measures the
tested pre-write failure path, not a universal request deadline during outages.
The new `RedisTimeoutConfigurationTests` also accepts TCP without answering
Redis commands and checks the real client's bounded failure. Existing
fail-closed throttles, commit/rollback, recovery and SSE tests still pass.

Evidence: [Redis interruption](validation/full-qa-redis-recovery-2026-10-30.json).

### Repeat the guarded HTTP tests

Prepare a separate private environment file with fresh secrets,
`DB_NAME=rosario_full_qa`, a dedicated QA database user, and unused/ephemeral
API/frontend ports. Start the backend/frontend Compose files with an explicit
`-p rosario-full-qa` project name and that environment file. Use `--no-build`
with the verified images. The functional harness creates its own fixtures;
representative history-load measurements additionally require a reviewed copy
restored into the separate QA database before application startup.

From the backend checkout, with the QA API/gateway healthy:

```bash
docker compose -p rosario-full-qa --env-file /private/qa.env \
  -f compose.yaml -f docker/compose.frontend.example.yaml \
  exec -T -e ROSARIO_QA_ALLOW_WRITES=isolated-qa-only api python - \
  < scripts/qa_http_check.py
```

The sanitized result is `/tmp/qa-http-result.json` inside the QA API container;
the private read-load tokens are `/tmp/qa-read-tokens.json`. Keep tokens outside
Git and copy them only into a mode-600 temporary file for `scripts/load_check.py`.
The load tool accepts a concurrency, duration, latency target and explicit API
paths. The frontend proxy requires the `/backend` prefix on those paths.
Never attach the working database volume or reuse its credentials for this QA
project. Remove only the disposable project/volumes after retaining its reports.

## Browser acceptance and frontend performance finding

The compiled Docker frontend passed a real staff/admin flow. A staff checkout
appeared in open, date-filtered admin history in **598 ms**, without reloading.
A second sale made while the admin was offline appeared after reconnect. The
date filter survived both updates; exactly two staff receipts were created and
stock changed from 10 to 7. Logout returned 200 and old access then returned
401. No browser exceptions or unexpected API failures occurred.

A prior synthetic-invalidation check passed at 490 ms. Both checks used one
authenticated browser context; the staff HTTP client was a separate identity.
These latency measurements apply to the short selected date range.

Opening **unfiltered** history with 4,861 receipts took **18.279 seconds** in the
first run and **19.164 seconds** in the real-sale run. The first run observed 52
history requests by initial render and 97 background order-page requests.
Source inspection identifies full-list pagination in `salesService.getAll()` /
`getAllPages()` and the admin KPI fallback that scans orders to count fulfilled
orders with pending payments. Background pagination continued after navigation.

The frontend request in `FRONTEND_HANDOFF.md` calls for server pagination,
aggregate reads for complete totals/payment counts and cancellation of obsolete
page chains. Reconnect resync and stale-response/session guards must remain.
Frontend source was not edited. This responsiveness issue must be resolved
before claiming immediate updates for unfiltered history at this dataset size.

Evidence: [browser/cache event](validation/full-qa-browser-2026-10-30.json),
[browser/real staff sales](validation/full-qa-browser-sales-2026-10-30.json).
